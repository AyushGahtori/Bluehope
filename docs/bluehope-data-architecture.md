# BlueHope Firebase Data Architecture

This document is the production data foundation for BlueHope. It treats Firebase Authentication as identity, Firestore as the primary structured database, and Firebase Storage as the binary/media layer. Email and phone are attributes only; Firebase UID is the stable identity key.

## Architecture Diagram

```text
Firebase Authentication
  -> users/{uid}
  -> role profiles
     -> customerProfiles/{uid}
        -> childProfiles/{childId}
     -> providerProfiles/{providerId}
     -> institutionProfiles/{institutionId}
        -> institutionStaff/{staffId}
  -> listings/{listingId}
  -> searchListings/{listingId}
  -> recommendationFeatures/{listingId}
  -> reviews/{reviewId}
     -> reviews/{reviewId}/replies/{replyId}
  -> enquiries/{enquiryId}
  -> bookings/{bookingId}
  -> conversations/{conversationId}/messages/{messageId}
  -> notifications/{notificationId}
  -> analyticsEvents/{eventId}
  -> auditLogs/{auditId}

Firebase Storage
  -> users/{uid}/profile
  -> customers/{uid}/documents
  -> providers/{providerId}/profile|gallery|videos
  -> institutions/{institutionId}/logo|gallery
  -> reviews/{reviewId}/media
  -> documents/{ownerId}/...
```

## Collection And Document Map

| Collection | Purpose | Required Fields | Key Indexes | Owner | Read | Write | Server-only Fields | Lifecycle |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `users/{uid}` | Account identity metadata linked to Firebase Auth | `uid`, `role`, `accountStatus`, `authProvider`, `createdAt`, `updatedAt` | document ID, `role`, `accountStatus` | Firebase UID | owner, moderator/admin | owner can update safe profile fields | `role`, `accountStatus`, `trustScore`, deletion fields | soft-delete on account closure; retain audit trail |
| `customerProfiles/{uid}` | Parent/family preferences and onboarding state | `uid`, `preferences`, `onboardingCompleted` | document ID, location fields as needed | Firebase UID | owner, moderator/admin | owner | internal risk flags | delete/anonymize on account deletion |
| `childProfiles/{childId}` | Private child/family-member support context | `childId`, `ownerUid`, `relationship`, `conditionIds`, `supportNeedIds` | `ownerUid + deletedAt + updatedAt` | parent/customer UID | owner only by default | owner | provider access grants, risk labels | soft-delete first, permanent deletion after retention window |
| `conditions/{id}` | Controlled diagnosis/support taxonomy | `id`, `slug`, `label`, `parentFriendlyLabel`, `active` | `slug`, `active`, `sortOrder` | system | public | admin/system | none | versioned, never casually renamed |
| `conditionSubcategories/{id}` | Structured condition support needs | `id`, `conditionId`, `label`, `active` | `conditionId + active` | system | public | admin/system | none | versioned |
| `services/{id}` | Controlled service catalog | `id`, `slug`, `label`, `category`, `active` | `slug`, `category`, `active` | system | public | admin/system | none | versioned |
| `providerProfiles/{providerId}` | Canonical sole provider profile | `providerId`, `ownerUid`, `listingId`, `displayName`, `serviceIds`, `conditionIds`, `profileStatus` | owner, service, condition, status | provider UID | public if active, owner, staff/admin | owner safe fields | `verificationStatus`, `ratingSummary`, `trustScore`, `adminNotes` | archived on provider closure |
| `institutionProfiles/{institutionId}` | Canonical organization/institute profile | `institutionId`, `ownerUid`, `listingId`, `organizationName`, `locations`, `staffUids` | owner, service, condition, location, status | institution owner UID | public if active, owner/staff, admin | owner/staff safe fields | verification, rating, trust, admin notes | archived; branches can continue independently |
| `institutionStaff/{staffId}` | Staff access map for institutes | `institutionId`, `ownerUid`, `staffUid`, `permissions` | `institutionId`, `staffUid` | institution owner | owner, staff member, admin | admin/system | permission grants | revoke instead of delete for auditability |
| `listings/{listingId}` | Public marketplace abstraction over providers/institutes | `listingId`, `ownerUid`, `ownerType`, `sourceId`, `title`, `serviceIds`, `conditionIds`, `location`, `ratingSummary` | status, service, condition, owner type, city | source owner | public active listings | system only | rating, trust, ranking | rebuilt from canonical profile changes |
| `searchListings/{listingId}` | Denormalized query/search projection | `listingId`, `normalizedTitle`, `searchTokens`, `serviceIds`, `conditionIds`, `city`, `geohashPrefix5`, `rankingFeatures` | see `firestore.indexes.json` | system | public active search docs | system only | all ranking fields | regenerated by backend sync jobs |
| `recommendationFeatures/{listingId}` | Recommendation-safe listing features | `serviceIds`, `conditionIds`, `ageGroups`, `coordinates`, `trustScore` | condition/service/age/status | system | authenticated | system only | scores | regenerated from listings and engagement |
| `reviews/{reviewId}` | Scalable reviews independent of listings | `reviewId`, `listingId`, `authorUid`, `rating`, `status`, `moderationState` | `listingId + status + moderationState + createdAt` | author UID | public only after approved/published | author safe fields; system moderation | moderation, fraud, helpful count | hidden/retained on moderation; anonymized if required |
| `reviews/{reviewId}/replies/{replyId}` | Controlled review replies/comments | `replyId`, `authorUid`, `text`, `moderationState` | collection-group by author/status if needed | author UID | follows parent review | author; moderation by system | moderation fields | limited nesting; no arbitrary recursion |
| `reviewReports/{reportId}` | Reports against reviews/replies | `reporterUid`, `reviewId`, `reason`, `createdAt` | `reviewId`, `reporterUid` | reporter UID | moderator/admin | reporter create; moderator update | resolution | retain for abuse history |
| `mediaAssets/{mediaId}` | Firestore metadata for Storage files | `mediaId`, `ownerUid`, `storagePath`, `contentType`, `sizeBytes`, `visibility`, `moderationState` | owner, ownerType, moderation | uploader UID | by visibility/owner/admin | owner safe metadata | moderation, derived variants | delete metadata after Storage cleanup |
| `savedProviders/{savedId}` | Customer shortlist | `customerUid`, `listingId`, `createdAt` | `customerUid + listingId` unique in backend | customer UID | owner | owner create/delete | none | delete with customer |
| `enquiries/{enquiryId}` | Customer-provider inquiry workflow | `customerUid`, `listingId`, `message`, `status` | `customerUid`, `providerUid`, `listingId`, `status` | customer UID | participants, moderator | participant safe fields | fraud/moderation | retain for service history, then archive |
| `bookings/{bookingId}` | Appointment lifecycle | `customerUid`, `listingId`, `serviceId`, `startsAt`, `endsAt`, `status` | customer/status/date, provider/status/date | participants | participants, moderator | participants by workflow; system finalizes | payment state, verified booking | legal retention, then archive/anonymize |
| `conversations/{id}` | Message thread metadata | `participantUids`, `relatedEntityId`, `lastMessageAt` | participants, lastMessageAt | participants | participants only | participants safe fields | moderation flags | retention policy by account state |
| `conversations/{id}/messages/{id}` | Message content | `senderUid`, `text`, `createdAt`, `readStatus` | createdAt, moderation | sender UID | participants | sender create only | moderation | archive/delete by retention |
| `notifications/{id}` | Per-user notifications | `recipientUid`, `type`, `title`, `read`, `createdAt`, `expiresAt` | recipient/read/createdAt, TTL | recipient UID | recipient | system create, recipient read/delete | none | TTL cleanup |
| `analyticsEvents/{id}` | Short-lived operational events | `actorUid`, `type`, `createdAt`, `expiresAt` | type/date, TTL | actor/system | server only | limited client create; backend preferred | device/IP hashes | TTL; export to BigQuery for warehouse |
| `auditLogs/{id}` | Append-only privileged action history | `actorUid`, `action`, `targetCollection`, `targetId`, `createdAt` | action/date, target | system | admin only | server only | all | long retention, immutable |
| `searchHistory/{id}` | Recent user searches for UX | `uid`, `query`, `filters`, `createdAt`, `expiresAt` | uid/date, TTL | user | owner | owner create/delete | none | TTL |

## Relationship Map

| Relationship | Implementation |
| --- | --- |
| Customer to child | `childProfiles.ownerUid` references `users/{uid}`; multiple child docs per customer. |
| Customer to saved provider | `savedProviders.customerUid` plus `listingId`; backend enforces uniqueness. |
| Customer to enquiry | `enquiries.customerUid`; provider/institution access only when named as participant. |
| Customer to booking | `bookings.customerUid`, optional `childId`, and `listingId`. |
| Customer to review | `reviews.authorUid`; review creation should require completed/authorized booking where possible. |
| Provider to listing | `providerProfiles.listingId` maps to `listings/{listingId}` and `searchListings/{listingId}`. |
| Provider to service/condition | `serviceIds` and `conditionIds` reference controlled taxonomy documents. |
| Provider to media/availability | `mediaAssets.ownerType = provider`; availability should be separate subcollection or top-level slots by provider/date. |
| Institute to listing/location/staff | `institutionProfiles.listingId`, `locations[]`, `institutionStaff` records, and `staffUids` for quick checks. |
| Listing to reviews/recommendations | `reviews.listingId` and `recommendationFeatures/{listingId}`. |

## Permission Matrix

| Role | Read | Create | Update | Delete | Approve | Moderate |
| --- | --- | --- | --- | --- | --- | --- |
| Customer | own user/profile/children, public listings, own conversations/bookings/enquiries | child, enquiry, booking request, review, saved provider | own safe fields, own draft/published review safe fields | soft-delete own child/saved provider | no | report content |
| Sole Provider | own provider profile, participant bookings/enquiries/messages, public listings | provider profile, replies, availability | own safe provider fields and workflow responses | no direct hard delete | no | report reviews |
| Institution | own institution profile and staff-scoped workflows | institution profile, staff invites through backend | safe institution fields | no direct hard delete | no | report reviews |
| Staff | assigned institution workflows only | replies/messages if allowed | assigned operational fields | no | no | report content |
| Moderator | public/private operational data required for safety | moderation records | moderation status, reports, content visibility | hide content | limited verification workflow | yes |
| Admin | all operational records except secrets outside Firestore | system records | roles/status/verification/index repair | privileged soft delete | yes | yes |
| System | all through Admin SDK | derived docs, audit logs, notifications, aggregates | derived docs, counters, moderation automation | scheduled cleanup | yes | yes |

## Security Rules Specification

The implemented rule files are:

| File | Scope |
| --- | --- |
| `firestore.rules` | UID ownership, role checks, public listing reads, private child data, protected aggregate/verification fields, append-only audit logs. |
| `storage.rules` | Owner-scoped upload paths, file type checks, size limits, private review media by default, provider/institution path ownership through custom claims. |

Important production hardening:

- Set custom claims (`role`, `providerIds`, `institutionIds`) only from privileged backend code.
- Keep child data unreadable by providers unless an enquiry/booking grants a narrow server-mediated view.
- Use Cloud Functions/backend writes for `listings`, `searchListings`, aggregate counters, verification, moderation, and audit logs.
- Enable Firebase App Check for web clients before launch.
- Add server-side rate limiting for searches, enquiries, messages, reviews, uploads, and auth-sensitive writes.

## Search Architecture

Firestore should handle structured MVP discovery:

- `searchListings` stores denormalized public fields: service IDs, condition IDs, city/locality, language, age band, geohash prefix, rating, availability flags, and ranking features.
- Firestore queries filter by realistic combinations from `firestore.indexes.json`, then application code ranks by eligibility, relevance, distance, availability, quality, and trust.
- Geosearch should use coordinates plus geohash/geofire range queries. Address text is display data, not distance data.
- Keyword search uses normalized tokens and service/condition aliases for MVP. Do not attempt arbitrary Google-like search with Firestore.
- Introduce Algolia, Typesense, Meilisearch, or OpenSearch when typo tolerance, synonym ranking, faceting, or large multi-field keyword search becomes a product requirement.
- Keep the canonical profile records separate so an external index can be rebuilt from `providerProfiles`, `institutionProfiles`, and `listings`.

Latency targets to benchmark after deployment:

- Search API p95 under 500 ms for first page with cached taxonomy.
- Profile API p95 under 350 ms for public listing details.
- Recommendation API p95 under 700 ms for first page after child/profile context is loaded.

## Recommendation Rule

Recommendations must follow:

1. Eligibility: service/condition/age/language fit.
2. Relevance score: taxonomy match strength and provider specialization.
3. Distance: only after relevance.
4. Availability: online, clinic, home visit, near-term slots.
5. Quality/trust: verification, completeness, review integrity, response rate.

Sensitive raw child information should not be copied into public ranking documents.

## Storage Structure

| Path | Content | Access |
| --- | --- | --- |
| `/users/{uid}/profile/` | user avatars | owner/admin read-write |
| `/customers/{uid}/documents/` | private intake docs | owner/admin only |
| `/providers/{providerId}/profile/` | public profile image | public read after upload; owner claim write |
| `/providers/{providerId}/gallery/` | provider gallery images | public read; owner claim write |
| `/providers/{providerId}/videos/` | provider videos | public read; size-limited owner write |
| `/institutions/{institutionId}/logo/` | logos | public read; institution claim write |
| `/institutions/{institutionId}/gallery/` | institution images | public read; institution claim write |
| `/reviews/{reviewId}/media/` | review uploads | private until moderation creates approved variants |
| `/documents/{ownerId}/...` | certificates and verification docs | owner/admin only |

Firestore stores storage paths, content type, size, dimensions, upload time, uploader UID, variants, visibility, and moderation state. Storage holds binary data only.

Media pipeline:

1. Upload original to a private or owner path with file size/type rules.
2. Backend validates metadata and creates `mediaAssets/{mediaId}`.
3. Processing job generates thumbnail/card/medium variants, preferably WebP/AVIF for images.
4. Moderation sets visibility and links approved variants to public listing/review surfaces.
5. UI uses thumbnail for cards, medium for profiles, and full optimized variants only in galleries.

Practical limits for MVP:

- Profile image: 5 MB.
- Gallery image: 8 MB.
- Review image: 6 MB, maximum 6 images per review.
- Provider video: 100 MB until a proper video pipeline/transcoder is added.
- No automatic public access for review media.

## Data Lifecycle

| Data | Creation | Update | Archive/Delete |
| --- | --- | --- | --- |
| User/customer | Auth sign-in plus `users/{uid}` upsert | owner safe fields; admin status/role | soft-delete, then remove private children/docs after retention |
| Child profile | owner creates | owner only | soft delete immediately; permanent deletion after retention unless legal hold |
| Provider/institute | owner creates draft | owner safe fields; system syncs listings | archive listing, remove from search index |
| Reviews | authorized customer creates | author safe edits; moderation controls status | hide on moderation, anonymize on account deletion when needed |
| Media | upload plus metadata doc | system variants/moderation | delete Storage object, variants, then metadata tombstone |
| Notifications/search history/analytics | created by app/backend | minimal updates | TTL cleanup |
| Audit logs | backend only | never update | long retention, restricted export |

Account deletion should remove or anonymize customer private data, revoke public listings, clean private media, remove search projections, preserve legally required booking/payment/audit records, and write an audit log.

## Retention And Backup

- Notifications: 30-90 day TTL.
- Search history: 30 day TTL unless user opts out earlier.
- Analytics events: export to BigQuery or analytics warehouse, then TTL raw Firestore events.
- Messages: product/legal policy dependent; support soft-delete per participant.
- Audit logs: at least 1-7 years depending on legal requirements.
- Firestore: enable scheduled backups/export and test restores quarterly.
- Storage: lifecycle policies for abandoned uploads, deleted variants, and old originals after optimized variants exist.
- Suggested early RPO: 24 hours. Suggested early RTO: 8 hours. Tighten after production usage and compliance review.

## Scale And Cost Analysis

Assumptions from the prompt:

- Provider media: 10 images/provider * 2 MB = 20 MB/provider.
- Review media: 100 customers/provider, 40% upload media, 3 images each, 2 MB/image = 240 MB/provider.
- Baseline media per provider: about 260 MB before thumbnails, videos, documents, backups, and derived copies.

| Scenario | Provider Images | Review Media | Baseline Media | Notes |
| --- | ---: | ---: | ---: | --- |
| 100 providers | 2 GB | 24 GB | 26 GB | Firebase Storage is mandatory from day one. |
| 1,000 providers | 20 GB | 240 GB | 260 GB | Download traffic and image variants become larger cost drivers than raw storage. |
| 10,000 providers | 200 GB | 2.4 TB | 2.6 TB | Requires automated lifecycle cleanup, CDN caching, moderation queues, and analytics export. |
| 100,000 providers | 2 TB | 24 TB | 26 TB | External search, warehouse analytics, and serious media ops are required. |

At large scale, cost drivers are separate:

- Storage size for originals and variants.
- Download/egress from profile cards, galleries, and videos.
- Firestore reads/writes for search, messages, bookings, counters, and notifications.
- Image/video processing and moderation.
- Backups/exports and analytics warehouse storage.

Firestore alone is sufficient for the MVP and structured filtering. Add external search when keyword quality, large faceting, or high-volume geosearch exceeds Firestore query ergonomics. Add BigQuery/Firebase Analytics when event volume makes Firestore a poor warehouse.

## Threat Model

| Threat | Impact | Mitigation | Detection | Recovery |
| --- | --- | --- | --- | --- |
| Unauthorized child reads | severe privacy breach | owner-only rules, backend-mediated sharing | denied-read logs, audit reviews | revoke access, notify, rotate tokens |
| Role escalation | admin/provider takeover | custom claims only from backend, protected fields | audit role changes | rollback claims/docs |
| Stolen token | account misuse | token revocation checks, App Check, sensitive reauth | unusual activity alerts | revoke sessions |
| Malicious uploads | malware/PII/public exposure | content type/size rules, moderation, private review media | moderation queue, reports | quarantine/delete media |
| Oversized uploads | cost abuse | Storage rule limits and backend limits | usage alerts | delete abandoned uploads |
| Spam enquiries/messages | provider harassment | rate limiting, abuse scoring | volume anomaly alerts | throttle/suspend |
| Fake reviews | trust manipulation | verified booking flags, fraud flags, moderation | review integrity dashboard | hide/recalculate aggregates |
| Scraping/enumeration | data extraction | App Check, pagination, rate limits, no child public data | traffic anomaly alerts | rotate keys/rules, block clients |
| Content injection | XSS/reputation risk | validate/sanitize text, render safely | CSP/reporting | remove content |
| Hot documents | write failures | distributed counters, append events | write latency/error monitoring | shard/migrate counters |
| Compromised admin | platform-wide risk | least privilege, audit logs, MFA | privileged action alerts | revoke admin, restore from backup |

## Development Environments

- Use separate Firebase projects for development, staging, and production.
- Keep `.env.local` and deployment secrets out of Git.
- Seed only development/staging with records marked `demo: true`.
- Never test against production child/customer data casually.
- Use the Firebase Emulator Suite for local rules testing before production deploys.
